# HumanFlow「问题与验证」优化方案

日期：2026-10-03
状态：P0、P1、P2 已实施，随 0.4.4 发布
基线：当前本地工作区代码，包含问题位置跟踪、多问题讨论、中英文 UI 及超时设置等未发布改动。

## 1. 建议结论

默认展示仍需关注的问题，将“已解决”和“不采纳”收进可搜索、可重新打开的“已结束”列表。第一阶段的归档采用视图归组，保留原记录和稳定 ID，不自动删除，也不另建一套归档存储。

“问题与验证”围绕三个动作组织：选择要处理的问题、核对相关验证证据、由用户确认结束。应用候选后进入“待验证”；命令成功仅作为证据，不能直接将问题标记为已解决。

实施顺序建议：先改善列表和统计，再建立问题与验证的关联，最后完善重复报告与长期记录管理。第一阶段即可解决已完成事项持续占用界面的主要痛点。

## 3. 页面结构

建议保留现有“问题与验证”标签页，在内部采用如下布局：

```text
问题与验证（待关注 7）
待处理 3 · 待验证 2 · 稍后处理 1 · 需复查 1
已解决 8 · 不采纳 2

[待关注] [待验证] [已结束] [全部]    [搜索标题 / 路径 / 编号]
[类型：全部 / 缺陷 / 简化建议]      [状态筛选]

已选 2 项    [讨论所选] [稍后处理] [标记处理结果] [清除]

F-012  问题标题                    待验证 · 位置待确认
src/example.js                    关联验证：1 条成功、1 条已过期
[展开依据与影响] [讨论] [查看验证] [标记已解决]

验证
[相关建议命令] [运行记录]
命令摘要 · 运行时间 · 结果 · 当前适用性 · 关联问题
```

### 3.1 默认列表与筛选

- 默认“待关注”：`open`、`pendingVerification`、`deferred`，以及已结束但再次被报告、等待人工复查的记录。
- “待验证”：只包含 `pendingVerification`；有成功验证仍留在这里，直到人工确认解决。
- “已结束”：`resolved`、`dismissed`。再次报告的记录仍保留原状态，同时在“待关注”中出现提醒；不得复制成两个问题对象。
- “全部”：用于完整查找与追溯。搜索和类别筛选在当前视图内生效，空结果提供“查看全部问题”。
- 默认排序：需复查、待验证、待处理、稍后处理；组内保持稳定创建顺序。已结束列表按关闭时间倒序，旧记录无时间时保留原顺序。
- 筛选、搜索、展开状态按任务保存到现有 `uiState`；数据刷新和语言切换保留阅读位置。
- 第一阶段超过 50 条时使用“加载更多”，默认只渲染 50 条；分页不改变数据或总数。是否引入虚拟列表由后续性能测量决定。

### 3.2 卡片精简

卡片默认只显示稳定编号、标题、文件位置、类别、状态及验证摘要。依据、影响、替代方案和处理历史放入详情，避免重复展示状态。

已结束卡片默认收起，主要动作是“查看处理记录”“重新打开”“讨论此记录”。“仅处理此问题”从已结束卡片的主要操作中移除；用户重新打开后恢复修复入口。

位置失效与问题是否解决分别显示。文件被删除、目标行消失或锚点无法唯一匹配，都不能据此认定问题已经修复。

### 3.3 数量与进度

优先展示状态数量，移除当前含义不清的“问题处理进度”百分比。若保留进度条，名称必须是“已结束记录”，分子只能是 `resolved + dismissed`，不能称为修复率。

“待关注”按问题 ID 去重计数：活动状态集合与需复查集合的并集。“需复查”是额外提醒，可能与状态重叠，不能把所有展示数字直接相加。没有待关注问题时显示“当前没有待关注问题，已结束记录可继续查看”，不能宣称项目不存在缺陷。

审查说明应绑定具体来源轮次：仅实际 `inspect` 轮次显示“本次只读审查未应用修改”。跨轮汇总使用“模型发现与人工处理记录”，验证覆盖范围单独说明。

## 4. 已解决问题的处理规则

### 4.1 关闭、收起与重新打开

1. 用户点击“标记已解决”，在卡片内展开简短表单：处理说明、可选关联验证记录，以及“仅人工核对”选项。
2. 支持没有自动化测试的解决方式，但要求选择确认依据；不把“未运行验证”伪装成验证通过。
3. 确认后保留原 ID，记录关闭时间与依据，移动到“已结束”，显示“已移至已结束 · 撤销”。撤销生成一次状态变更记录，恢复关闭前的状态。
4. 用户可以随时重新打开，状态回到 `open`，关闭依据保留在历史中。人工重新打开不自动执行模型请求或验证命令。
5. “不采纳”使用独立入口和原因，例如误报、不符合目标、暂不接受该简化方案；“稍后处理”不进入已结束列表。

第一阶段不提供自动删除已解决问题。后续如确有存储整理需要，可增加显式导出与清理功能，须先展示影响范围；删除不是默认归档行为。

### 4.2 状态转换

| 触发 | 处理规则 |
| --- | --- |
| 新发现问题 | 进入 `open` |
| 用户暂缓 | 进入 `deferred`，仍在待关注中 |
| 针对该问题的候选被应用 | 进入 `pendingVerification`，同时展示是否部分应用、是否保存成功 |
| 批次只应用了部分片段或保存失败 | 不自动结束问题；提示修复与磁盘验证可能尚不完整 |
| 验证命令退出码为 0 | 新增验证证据，问题状态不变 |
| 验证失败、取消或失效 | 展示结果和原因，不自动改代码或改变人工关闭结论 |
| 用户确认解决 | 进入 `resolved`，保存依据并归入已结束 |
| 用户不采纳 | 进入 `dismissed`，保存原因并归入已结束 |
| 用户重新打开 | 回到 `open`，保留先前处理记录 |
| 已关闭问题再次被模型报告 | 保留关闭状态，增加“再次报告，需复查”提醒并进入待关注视图 |

关闭记录所依据的代码后来变化，应标注“原验证对当前代码的适用性待确认”，保留当时的人工结论。不能因为任意文件变化而把所有已解决问题重新打开。

### 4.3 重复报告与复查

第一阶段继续使用现有严格匹配规则，避免凭相似标题错误合并不同问题。匹配已结束记录时，将本次报告保存为新的观察记录，冻结原关闭依据，不覆盖关闭时的标题、证据、位置快照。

用户复查后可以“重新打开”，或“维持已结束”并记录原因。后者仅确认本次报告已处理，不永久屏蔽未来审查。模型只提出发现或复查建议，不自动撤销人工状态。

模型措辞变化而无法严格匹配时，仍新增问题。基于路径、符号、邻近代码的相似重复检测列为后续能力，只提示可能重复，由用户确认合并；第一阶段不做自动语义合并。

## 5. 问题与验证的关联

### 5.1 验证建议与运行结果分开

验证建议具有稳定 `checkId`，记录来源轮次和批次；每次运行生成独立 `validationId`。同一条命令多次执行不得覆盖旧结果。

当前“每轮替换 checks”的行为应调整为保留必要的历史建议：界面默认展示最新一轮及当前所选问题关联的建议，其他建议放到历史中。复用旧命令时重新展示命令、目录、原因及关联问题，由用户核对后执行。

问题与验证采用多对多关系。一次测试可关联多个问题，一个问题也可能需要多个测试及人工检查。初期由用户选择关联对象；模型提供的关联只能作为建议，不能凭文件相同或退出码成功推定覆盖。

### 5.2 验证记录展示

| 维度 | 展示内容 |
| --- | --- |
| 执行事实 | 命令、工作目录、开始/结束时间、退出码、成功/失败/取消/未知 |
| 关联对象 | 问题稳定编号、来源轮次、应用批次，可跳转 |
| 适用性 | 记录时有效 / 当前已过期 / 覆盖不完整，以及已知原因 |
| 覆盖范围 | 已记录版本的文件与检查方式；未知依赖明确标为未知 |
| 后续操作 | 核对后重新运行、查看关联问题、分析用户选取的错误输出 |

第一阶段沿用现有保守失效策略，增加原因说明；不直接缩小失效范围。测试可能依赖配置、依赖库、生成文件或未跟踪代码，仅检查少数文件不足以证明结果仍然适用。

将来若优化失效策略，必须先明确验证覆盖与依赖来源；不能只按问题文件相同就认定覆盖。扩展重启后对旧记录保留“需重新核对”的保守标记。

### 5.3 关闭时选择证据

- 优先列出已关联、成功且未过期的运行记录，并展示时间和覆盖范围。
- 过期、失败、取消的记录可作为历史引用，但不能标为“有效通过证据”。
- 没有合适运行记录时，用户可以选择“仅人工核对”，补充简短说明后关闭。
- 即使所有命令成功，最终关闭仍由用户确认。退出码成功并不证明语义正确或完整覆盖该问题。
- 已关闭问题的详情可追溯当时采用的证据；后续重跑不改写此前关闭记录。

## 6. 批量操作与多问题讨论

保留当前最多选择 50 个问题的限制，扩展为“讨论所选”“稍后处理”“标记处理结果”“重新打开”等动作。批量结束时先展示问题数量和具体编号；每个问题的依据与证据分别保存，不将一条测试自动视为覆盖所有选中问题。

筛选、切换视图或翻页时，清除列表操作中已经不可见的勾选，并给出提示，避免批量操作隐藏记录。输入区已加入的讨论引用独立保留，显示引用标题和数量；用户发送前仍可移除。不能因为问题被收起就悄悄丢掉尚未发送的引用。

问题列表勾选、讨论附件、模型建议的修复对象应使用不同的数据字段。多问题讨论不自动进入多问题修复；候选只有在明确关联修复对象、用户实际接受相关修改后，才将相应问题设为待验证。

状态修改通过扩展宿主统一校验任务 ID、问题 ID 和预期记录版本。批量请求先完整校验，再统一持久化并发布快照；任意记录已变化时保留当前状态，提示用户刷新后重试，避免部分状态静默更新。

## 7. 数据与兼容方案

沿用 `task.findings`、`task.validations` 和现有 UUID。本次实现采用下列增量字段（处理说明同时保存在状态事件的 `reason` 和关闭依据的 `note` 中）：

| 对象 | 新增字段建议 | 用途 |
| --- | --- | --- |
| finding | `displayNumber`、`createdAt`、`updatedAt`、`revision` | 稳定展示编号、排序及并发校验 |
| finding | `statusHistory[]` | 记录状态前后值、时间、用户操作、原因和可选关闭依据 |
| finding | `latestObservation`、`needsReview` | 保存再次报告的来源轮次及摘要；与人工状态独立 |
| 状态历史中的关闭依据 | `method`、`note`、`validationIds`、`snapshot` | 区分人工核对/结合运行验证，冻结当时问题证据和已知代码版本 |
| check | `id`、`findingIds`、`turnId`、`batchId` | 保留建议来源及经确认的关联 |
| validation | `checkId`、`findingIds`、`staleReason` | 将既有运行记录关联回问题并解释失效 |
| task | `nextFindingNumber`、问题数据迁移标记 | 新编号单调递增，迁移可重复执行而不重编号 |
| task.uiState | 问题视图、筛选、搜索、展开项及分页位置 | 跨刷新、语言切换和任务恢复保留阅读状态 |

不需要独立 `archived` 状态；“已结束”由当前状态派生。历史归档和问题解决含义不同，避免以后出现“已解决但不算已结束”等组合歧义。

旧记录迁移规则：

1. 保留 UUID、现有状态和原始问题内容；按原数组顺序一次性分配展示编号。
2. 不伪造创建时间、关闭时间或验证依据；缺失信息显示“旧记录，未记录处理依据”。
3. 旧 `resolved` / `dismissed` 直接归入已结束列表，用户仍可重新打开。
4. 旧验证记录缺少 `findingIds` 时显示“未关联具体问题”，不根据批次或文件自动补配。
5. 迁移函数幂等，能够处理缺失字段；先在任务副本中完成校验，成功后再写回现有存储。
6. 第一阶段不提升任务顶层 `version` 以致旧恢复函数丢弃整项任务；新增问题数据迁移标记，升级后核对讨论、批次与验证记录仍完整。

历史记录先保留，界面按需加载；分页不能顺手裁掉底层证据。存储保留期限、导出格式和不可逆清理另列后续设计。

## 8. 模型上下文策略

默认继续发送活动问题，不发送完整已结束列表与全部状态历史。为减少模型把历史问题再次当成待办，可附带有界的近期关闭摘要：最多 20 条、总计最多 4000 字符，包含 ID、简短标题、状态和关闭原因摘要，并明确省略数量。

用户显式引用已结束问题时，按所选 ID 补充该问题及其关闭依据摘要，提示模型区分历史结论和当前代码。再次报告且等待复查的记录进入本轮待关注上下文，带上原人工状态，避免模型误认为已经重新打开。

关联验证不能只取全任务最后十条：优先提供本次所选问题关联的必要记录，再补近期结果；去重并设置总预算。完整终端输出仍需用户选取、遮盖和确认，不能因自动关联而全部上传。

显式选择的必要信息超过预算时说明原因并要求减少本轮对象，不能无提示地省略用户选中的问题。最终请求仍遵守现有总上下文限制。

| 阶段 | 交付范围 | 主要修改位置 | 完成标准 |
| --- | --- | --- | --- |
| P0：列表与已结束管理 | 默认待关注、已结束视图、搜索/筛选、收起卡片、稳定编号、正确计数、单项关闭说明和重新打开 | `media/panel.html`、`media/panel.js`、`media/workspace.js`、`media/panel.css`、`media/i18n.js`、`src/vscode/workflow.mjs`、`src/vscode/task-workflow.mjs`、`src/vscode/extension.cjs` | 旧任务完整恢复；已解决事项不挤占待办；关闭可追溯且可撤销 |

## 10. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 存在 10 个已解决、2 个待处理问题 | 默认只显示 2 个待关注问题；已结束列表能查到全部 10 个旧问题 |
| 将待处理改为稍后处理或待验证 | 仍计入待关注，不增加已结束数 |
| 仅有不采纳和已解决问题 | 待关注为 0；分别显示解决与不采纳数量，不显示“全部已修复” |
| 标记解决后撤销、再重新打开 | UUID 和展示编号不变，状态和处理历史正确 |
| 筛选、排序、翻页、删除其他记录 | 同一问题的展示编号不漂移 |
| 问题被收进已结束时仍有讨论草稿 | 草稿和已附问题引用保留；不可见的列表操作勾选被清理 |
| 单问题修复只应用部分片段或保存失败 | 保留待验证及完整应用结果，不能自动解决 |
| 一条测试关联两个问题 | 两个问题都能查看该次运行；是否关闭分别人工确认 |
| 成功测试后代码发生变化 | 测试记录显示过期及原因；原关闭依据仍可追溯 |
| 测试取消、未知退出码或没有运行记录 | 不显示验证通过；支持明确的人工核对关闭方式 |
| 已结束问题被再次严格匹配报告 | 出现待关注提醒，保留旧结论和新观察，用户可重新打开或维持关闭 |
| 标题类似但证据不同 | 不自动合并为旧问题 |
| 旧任务升级并连续迁移两次 | 不丢状态、讨论和验证记录，不重编号，不补造时间 |
| 批量请求来自旧快照或其他任务 | 全部校验后拒绝过期请求，不出现部分静默更新 |
| 切换中文/英文、窄窗口及键盘操作 | 标签翻译完整；筛选、焦点、展开状态和草稿保留；状态不只用颜色区分 |
| 500 条混合状态问题、200 条验证记录 | 首屏按需渲染；筛选、选择和输入无明显阻塞；测试记录环境及测量结果 |

- **P0 完成**：四种视图、搜索与筛选、稳定编号、正确状态计数、折叠详情、关闭依据表单、撤销和重新打开。筛选、展开状态与分页位置按任务保存；列表操作与输入区讨论引用分开保存。

- **P2 完成**：再次报告的已结束问题以 `needsReview` 提醒复查，原关闭快照保持不变；复查可维持已结束或重新打开。默认上下文发送活动问题、最多 20 条/4000 字符的关闭摘要，并补充明确引用的问题与必要旧验证；验证摘要预算 24000 字符，必要记录超限会说明原因。
