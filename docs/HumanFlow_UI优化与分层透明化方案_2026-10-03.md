# HumanFlow UI 优化与分层透明化方案

方案日期：2026-10-03。实施记录更新：2026-10-04。

状态：已在本地 0.4.5 开发版实施并验证。阶段 A、B 已实现，阶段 C 首版限于公开事件与请求组成的按需诊断；不归档原始协议包、完整请求、内部思维或完整工具输出。下文保留设计依据，第 10 节记录实际交付和验证范围。尚未发布此版本。

适用范围：HumanFlow 面板的信息层级、每轮执行过程展示、上下文说明和诊断入口。保持用户审查后显式应用候选的工作方式。

配套资料：[UI、上下文效率与持续协作](HumanFlow_UI_Context_Optimization_Plan.md)、[同类工具 UI 与交互调研](HumanFlow_UI_Interaction_Research.md)、[面板生命周期与候选保护](HumanFlow_面板生命周期与候选保护方案.md)、[问题与验证优化方案](HumanFlow_问题与验证优化方案.md)。

## 1. 结论

建议增加透明度，默认展示足以判断和决策的信息，详细过程按需展开。优先优化现有信息的组织，再增加过程回查和诊断能力。

用户在主界面应能快速回答：

1. 当前在处理哪个任务、关注哪些代码？
2. 模型正在做什么，是否还在产生进度？
3. 本轮给出了什么结果，有哪些候选尚未应用？
4. 有什么依据和验证结果，下一步需要我做什么？

“尽量多呈现 Codex 内容”不作为独立目标。公开摘要、操作事件、来源和结果有助于用户判断，但全量日志常驻会增加阅读负担。透明度和界面密度应分别控制。

实施顺序：**主界面层级优化 → 每轮过程回查 → 按需诊断明细**。

## 3. 信息分为三层

| 层次 | 展示内容 | 默认方式 | 用户用途 |
| --- | --- | --- | --- |
| 当前状态 | 当前任务、关注对象、执行阶段、总等待时间、最近进度时间、待操作状态 | 常驻简短状态条 | 判断是否等待、取消、审查或继续讨论 |
| 本轮过程与依据 | 实际收到的摘要、进度说明、命令与工具调用、已知上下文来源、验证证据 | 每轮独立入口，默认折叠 | 理解本轮结果、核对依据、回查失败位置 |
| 诊断明细 | 选定轮次的公开事件和请求组成；失败响应沿用原有命令入口 | 独立入口，按需加载 | 排查连接、协议或上下文问题 |

异常和需要用户操作的事项可以主动显示简短提示；不自动展开整段日志，也不打断用户正在阅读的历史。

### 3.1 展示事实与未知状态

- 使用“执行过程”“服务端摘要”等名称；不将摘要标为完整思维链。
- 仅展示实际收到或能从本地状态确认的信息，注明来源。
- 没有摘要时显示“未返回摘要”，保留已收到的操作事件。
- 没有用量时显示“未知”，不以字符数换算出看似精确的 Token 数或费用。
- 没有完整读取追踪时标注覆盖限制，不声称“已检查全部文件”。
- 已发送上下文、工具读取结果、允许修改范围分别表达，读取资料不自动扩大写入授权。
- 保留模型回复的原文查看能力；界面整理不能将生成建议描述为已经完成的修改。

### 3.2 不同完成状态

“回答完成”“候选已生成”“已应用”“已保存”“验证命令成功”“问题人工确认已解决”分别代表不同事实，不能合并为一个“完成”状态。

不展示没有可靠依据的进度百分比。等待时间较长时提供最近进度时间、取消入口和连接状态，不能仅因一段时间没有事件就断言模型卡死。

## 4. 主界面优化

### 4.1 顶部状态区

顶部集中显示任务名称、简短关注对象和当前阶段。长期目标保留完整编辑入口，顶部只显示必要摘要。

示例：

```text
任务：修复配置读取
关注：src/config.ts · 选区 20–48
正在检查上下文 · 已等待 00:42 · 最近进度 3 秒前
```

时间和阶段来自实际状态。正文更新不反复改变整个顶部高度；低频任务操作放入已有菜单，避免扩展常驻按钮数量。

### 4.2 输入区与上下文

在输入区附近显示简短的上下文标签，例如关注文件、选区、附加材料和引用问题。点击标签查看来源或内容，修改与移除仍经过原有权限、归属和候选失效检查。

“更新关注点”和“选择文件作为关注点”保持可发现，不能因简化布局而藏到难以找到的位置。状态中区分“当前选择”和“本轮实际发送的版本”，避免编辑文件后误以为上一轮已看到新内容。

配置、完整上下文 JSON 和历史诊断放到明确入口，不要求用户每次发送前处理。

### 4.3 每轮结果与下一步

每轮末尾提供简短结果摘要，连接本轮对应的候选、问题和验证。建议包括：

- 主要结论与必要说明。
- 候选涉及文件数、当前处理状态；没有候选时不展示空的修改操作。
- 验证是否运行、结果是否仍对应当前代码。
- “查看候选”“讨论此结果”“查看过程”等与本轮对象直接关联的动作。

结果摘要使用已有结构化结果和本地记录，不额外请求模型生成另一份解释。没有可靠跨文件检查记录时，不展示“依赖检查已通过”。

### 4.4 减少重复信息

保留应用前必须知道的影响、保存行为和必要确认。静态说明可以收进帮助或详情，避免在多张卡片中重复占据正文空间。

宽屏可保留请求目录；窄屏优先展示当前讨论和输入区，目录按需展开。切换视图、展开详情和进度更新都应保留草稿、勾选、滚动及键盘焦点。

## 5. 每轮执行过程

### 5.1 执行中与完成后

执行中显示最新的有效动作和简短阶段；查看详情时展示本轮时间线。完成后收成一行摘要，例如“回答完成 · 8 项过程事件 · 查看过程”。

用户主动展开的详情不因后台刷新而被收起；用户阅读旧记录时不强制滚动到最新事件。

### 5.2 事件归属与合并

建议过程记录关联任务 ID、轮次 ID 和事件 ID，保存类型、时间、状态、正文及来源。新增展示字段不替代宿主的消息归属校验。

- 同一命令的开始和结束更新同一条记录，保留退出状态。
- 同一摘要的流式增量合并更新，避免每个分片成为一个列表项。
- 工具调用按实际生命周期更新，来源或结果缺失时明确标注。
- 取消、失败、断线和超时作为明确终止状态，不伪装为正常完成。
- 新轮次开启后，上一轮摘要仍能回查；重启后未完整恢复的记录标注缺失范围。

### 5.3 读取范围与工具输出

第一阶段沿用已收到的命令和工具元数据，不解析命令字符串来承诺完整读取清单。

后续若接入更多工具输出，应区分输入、输出和执行状态，设置长度限制，按需展开。文件读取清单必须有可靠事件来源；混合命令、重定向、工具内部读取和未上报操作都可能使追踪不完整。

## 6. 轻量化与数据边界

### 6.1 三种成本分别控制

| 成本 | 控制方式 | 容易产生的误解 |
| --- | --- | --- |
| 视觉负担 | 简短状态、每轮折叠、按需诊断 | 折叠只是降低默认信息密度 |
| 渲染与存储 | 增量更新、按需挂载、有界记录、历史分段加载 | 不显示的事件仍可能占内存与持久存储 |
| 模型用量 | 复用已有事件，不额外生成过程解说；分别控制请求内容 | 隐藏或折叠输出不会减少已经生成的模型用量 |

过程详情的展开和收起是本地动作，不请求模型。需要模型进一步解释时，使用单独且明确的动作，并注明会发送新请求。

### 6.2 有界记录

首版沿用现有每轮 60 项、每项最多 6000 字符的上限作为起点，新增按轮历史时还须设置任务级总字节上限，不能把每轮上限无限累加。

截断和淘汰必须可见，例如“较早过程已省略”“本条仅保留部分文本”。保留必要的轮次结果和终止状态，不因丢弃早期进度事件而显示错误的执行结论。

本地首版确定任务级过程记录上限为 256 KiB、最多保留 30 轮，超过任一条件时淘汰较早过程；上下文最多归档 50 个文件明细，前端缓存最多 3 轮详情。第 10 节提供合成负载测量；这些是首版预算，不能据此推断真实远程模型或 VS Code 启动性能。

### 6.3 隐私与诊断

过程记录可能含代码片段、文件路径、命令参数和外部工具内容。默认仅在本地按既有任务记录边界保存，不新增自动上传或全量遥测。

诊断导出提供轮次与范围选择、可编辑预览及常见凭据遮盖。首版不保存或展示原始请求；失败响应沿用已有“查看最近失败响应”命令。自动遮盖不能保证识别全部敏感信息。

诊断入口不能读取或展示 API Key。新增记录应纳入任务删除规则；不能将删除本地任务描述为同时清除了 Codex 侧历史。

## 7. 分阶段实施

| 阶段 | 工作内容 | 交付目标 |
| --- | --- | --- |
| A：主界面层级 | 顶部简短状态、输入区上下文标签、每轮结果操作、静态说明整理 | 日常讨论与候选审查更容易定位，不扩大默认日志展示 |
| B：过程回查 | 按轮关联过程、时间线合并、失败与取消状态、有界归档和按需渲染 | 能回查本轮依据和终止原因，保持长会话可用 |
| C：诊断入口 | 公开事件与请求组成、范围选择、预览与脱敏导出 | 用户需要时能排查问题，不影响普通工作流程；原始协议与完整请求留作后续单独评估 |

各阶段分别评审和验收。优先复用现有 Webview、状态管理、设计资产和原生 Diff，不为透明化重写整个前端或重复实现 Codex 执行循环。

涉及展示与宿主消息变更时同步处理协议兼容；安装新版后仍遵循已有重载窗口要求。

## 8. 验收标准

以下为实施验收要求。已完成的自动化与视觉检查见第 10 节；不将未覆盖的真实远程推理或辅助技术检查计为通过。

### 8.1 信息与行为

- 主界面能够辨认当前任务、关注对象、阶段和需要用户采取的动作。
- 每轮过程与该轮候选、问题、验证正确关联；旧回合和其他任务事件不会混入当前轮。
- 未收到摘要、用量或完整读取记录时显示未知或覆盖限制，不补造数据。
- 完成、应用、保存、验证和问题关闭的状态分别表达。
- 过程展开与历史查看不发起模型请求，不自动应用候选或执行命令。
- 失败、取消、超时和重启恢复后仍能辨认实际状态和记录缺失范围。

### 8.2 交互与可访问性

- 宽屏和窄屏均保留主要动作；操作名称与中英文界面同步。
- 可使用键盘完成导航、展开、取消和查看候选；焦点与 ARIA 状态表达正确。
- 大量进度刷新不清空草稿、丢失勾选、折叠用户已展开的内容或抢占阅读位置。
- 原有候选失效检查、关闭确认、部分应用和保存规则保持有效。

### 8.3 性能与验证方式

- 构造连续摘要增量、重复生命周期事件和大量历史轮次，检查事件合并、归属和截断提示。
- 比较折叠与展开状态下的渲染开销，确认不会每次刷新都挂载全部历史详情。
- 检查任务级字节预算及重启恢复耗时，明确实际测量环境和结果。
- 按改动范围运行单元测试、浏览器交互、真实 Webview 与宿主恢复检查；不能用浏览器测试替代宿主消息往返验证。
- 检查原始记录与导出范围，确保不包含凭据、不自动上传，也不因新增诊断入口扩大文件写入权限。

## 9. 设计依据与后续决策

VS Code 官方建议 Webview 保持主题兼容、支持可访问性、使用恰当的命令入口，并避免重复已有编辑器功能。本方案据此继续使用原生 Diff、设置和任务执行能力。[官方 Webview UX 指南](https://code.visualstudio.com/api/ux-guidelines/webviews)

顶部状态区、过程保留预算、按轮持久化范围和首版诊断导出已按第 10 节确定。后续根据真实使用反馈调整密度和预算；接入更多原始事件或工具输出前另行评估来源、隐私和开销。

透明化的优先目标是让用户理解当前状态、结果依据和操作后果。日常界面保持简洁，详细证据能够回查，未知和未覆盖内容如实标注。

## 10. 本地实施与验证记录（2026-10-04）

### 10.1 实际交付

- 顶部显示当前关注文件与选区、任务目标摘要、执行阶段、等待时间和最近可见进度，不生成进度百分比。
- 输入区提供当前关注、最近发送上下文标签以及“更新关注点”“选择文件”。窄面板使用短按钮和紧凑标签，完整说明保留在提示中。
- 每轮末尾连接候选、历史批次、讨论与诊断；“讨论此结果”追加引用并保留已有草稿。候选、验证和人工问题状态仍使用原有记录。
- “执行过程”默认折叠，仅在轮次和过程均展开时加载公开事件；重复事件更新原节点，收起后取消详情订阅并卸载正文。不会为回查额外请求模型。
- 按轮保存公开摘要、命令与工具元数据、终止状态，以及发送时的上下文组成、文件来源与版本。当前关注变化不会改写历史发送版本。无摘要、截断、淘汰、旧记录未归档和重启中断均有提示。
- 每轮与扩展设置提供诊断入口，选择过程或上下文范围后生成可编辑 JSON 预览；保存使用 VS Code 原生文件对话框，仅支持本地 `.json`。取消、保存和错误在预览内反馈。
- 中英文静态与动态文案同步。面板协议由 7 更新为 8，安装后需重新加载窗口，避免新页面与旧宿主混用。

### 10.2 数据与成本边界

| 项目 | 首版设置 |
| --- | --- |
| 每轮事件 | 最多 60 项，每项最多保留末尾 6000 字符 |
| 任务级过程 | 记录 JSON 总计最多 256 KiB，最多 30 轮；先淘汰较早过程，保留轮次结论 |
| 上下文归档 | 最多 50 个文件明细，包含来源与版本，不含文件正文；超限显示省略数量 |
| 前端详情缓存 | 最多 3 轮；正文按展开状态挂载 |
| 实时刷新 | 过程消息约 100 ms 合并；执行中状态约每秒保存，终止时最终保存 |
| 额外模型请求 | 查看、折叠、诊断预览和保存均为 0；继续讨论仍由用户显式发送 |

首版诊断是规范化后的公开字段，不是原始协议抓包，也不是完整思考、读取轨迹或请求原文。摘要和操作文本可能包含代码片段或路径，先遮盖常见凭据再保存，用户导出前仍需核对。新增记录使用已有本地任务存储，随本地任务删除；不新增上传。

### 10.5 “结合运行验证”无可选记录的修复（2026-10-04）

用户反馈选择该依据后没有可勾选的记录，无法归档。排查确认：旧表单只列出已关联当前问题、成功且未过期的验证，没有提供直接补齐依据的操作；表单打开后也不会随验证记录变化重新生成列表。

已在解决表单中增加两条显式路径：确认覆盖后关联已有成功记录；核对具体命令后运行建议或重跑关联记录。问题表单的运行操作只关联本次新运行记录，不自动推断覆盖或改变原建议的关联。运行前校验任务、问题和命令记录版本，原生确认中显示问题编号、命令、目录和原因；取消确认不运行、不生成依据。

验证记录变化时重新生成可选列表，保留处理说明和确认方式，移除已过期的勾选；切换为人工核对时同时清空提交依据和可见勾选。宿主拒绝提交的原因直接显示在表单中。成功记录出现后仍需用户勾选、填写说明并确认，才归入“已结束”；没有运行验证的人工解决仍使用“仅人工核对”。

验证：107 项完整测试通过；追加验证版本冲突、取消原生确认、直接关联运行记录、动态列表刷新和确认方式切换的回归检查通过。真实 VS Code Webview 从空依据表单发起 `echo HumanFlow-test`，核对并点击原生命令确认，实际任务执行成功后在原表单勾选新记录并归档，未新增模型回合。日志位于 `dist/finding-validation-*.log`，本地 0.4.5 安装包已重新生成。
