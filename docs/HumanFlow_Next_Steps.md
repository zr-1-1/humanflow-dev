## 1. 目标与原方案调整

HumanFlow 的目标是让人能持续理解和掌握 AI 辅助开发的结果。AI 可以检查整个项目、解释不熟悉的 API，并提出或协助完成跨文件修改；用户无需手敲所有代码，但应能理解修改目的、关键逻辑和影响范围。

后续按完整工作流程交付，减少逐个添加按钮的零散迭代。每次模型修改仍围绕同一逻辑意图，避免把扩大产品开发阶段误解为允许模型无边界改动业务项目。

与原方案的关系：

- 保留“人掌握方向、广泛读取、修改可审查、按需解释”的原则。
- 调整“先建设多种工作模式、最后实现界面”的顺序，优先完善已有 VS Code 面板。
- Discuss、Inspect、Compare、Review 等作为自然交流中的能力，不要求用户依次执行固定步骤。
- 保留项目检查、问题记录、上下文解释的方向，按实际工作需要逐步接入。
- 继续优先使用 Codex App Server，暂不扩展第二套 harness。

参考：[工作流设计](HumanFlow_AI_Engineering_Workflow_Design_update.md)。该文档保留设计背景；与本文冲突的后续实施顺序以本文为准。当前已实现行为以 [README](../README.md) 和代码为准。

## 2. 当前基础与缺口

已有基础包括 Codex App Server 连接、模型与推理强度选择、选区讨论、项目级读取、跨文件候选建议、差异预览、按片段接受以及应用后保存。

当前模型以只读方式生成建议，由插件执行用户接受的修改。后续继续沿用这一职责划分。

主要缺口：

- 应用修改或手动编辑后需要重新绑定，重新绑定会清空讨论，打断连续开发。
- 面板历史与模型实际上下文可能不一致；旧讨论显示在界面上，不等于后续请求仍携带它。
- 尚未形成可恢复的任务记录，也不能自然地从无选区的项目问题开始。
- 候选建议主要通过静态检查和单元测试验证，真实扩展宿主中的写入、保存、撤销与冲突处理仍需验证。
- 当前批次快照在收到模型结果后建立，尚不能完整追踪模型读取期间的上下文变化。

## 3. 第一阶段：持续协作工作区

**作为下一轮整体实现范围，同时补齐关键写入流程的集成验证。**

### 3.1 任务与关注点分离

任务保存目标、讨论和处理记录；关注点保存当前文件、选区或符号。切换关注点不再等同于重新开始任务。

- 支持不选代码直接提出项目级问题。
- 支持在同一任务内切换文件、重新选择代码和继续追问。
- “新建任务”与“更新关注点”使用不同操作，避免误清空讨论。
- 以工作区隔离任务；不能把一个项目的上下文自动带入另一个项目。

### 3.2 修改后继续讨论

接受部分建议、保存或手动编辑后，保留任务历史，并在后续请求中同步实际代码状态。

同步至少区分：已应用片段、未应用片段、应用失败、保存成功或失败，以及用户后续编辑。应用与保存分别记录，保存失败不应被描述为修改未发生。

旧建议与当前代码不一致时，使相关批次失效并提示重新生成；不直接把旧建议覆盖到新代码上。讨论可以保留，旧批次的可应用资格不能因此保留。

对于未保存文件，以编辑器内容为准。上下文过大时应明确说明省略范围，不能悄悄用磁盘旧内容替代编辑器内容。

### 3.3 本地恢复与会话衔接

- 保存任务目标、必要讨论、关注位置和批次处理记录，支持关闭面板后恢复。
- 本地任务记录独立于模型线程；连接失败或线程无法恢复时，可以重建模型上下文。
- 恢复时核对工作区和当前文件状态；历史候选不能恢复后直接视为有效。
- 明确显示上下文恢复或重建状态，避免用户误以为模型拥有完整历史。
- 首期将记录放在扩展的工作区存储中，不默认写入业务仓库；提供删除任务记录的入口，不保存认证凭据。

### 3.4 阅读与反馈

- 支持安全渲染的 Markdown、代码高亮及文件位置跳转。
- 显示读取与生成进度；只展示实际可获得的执行信息，不虚构模型活动。
- 修改说明优先交代目的、关键行为和跨文件关系，API 细节按需展开。
- 继续支持取消请求、模型选择和推理强度选择。

### 3.5 建议实现拆分

| 模块 | 职责 |
| --- | --- |
| 任务状态 | 管理任务、关注点、讨论、批次和实际应用结果 |
| 上下文同步 | 组织当前代码、编辑状态、历史摘要和接受结果 |
| 本地存储 | 按工作区保存与恢复任务，管理存储版本 |
| 会话适配 | 复用或重建 Codex 会话，明确上下文是否连续 |
| 面板 | 展示任务状态、解释、差异和用户操作 |

优先从现有扩展中抽离这些职责，避免全部堆入面板事件处理函数；不为尚未接入的其他后端预先建立复杂抽象。

### 3.6 验收标准

1. 无选区时可提出项目问题，再选择某段代码继续同一个任务。
2. 切换关注文件后，既有讨论不清空，模型能获得新的关注点。
3. 接受一部分建议并手动修改后，可以直接追问；模型获知实际应用结果和当前相关代码。
4. 旧批次不能覆盖后来修改的内容，冲突能定位到相关文件。
5. 关闭并重开面板后可恢复任务；扩展重启后的恢复也有明确行为。
6. 请求失败或取消后，后续讨论的上下文状态与界面提示一致。
7. 在真实 VS Code 扩展宿主中验证部分应用、保存失败、用户撤销、未保存内容和冲突场景。

## 4. 第二阶段：从全局检查到可选择的修改

将原方案中的项目检查接入同一个任务流程：

> 提出问题 → 检查相关文件 → 展示问题和依据 → 选择处理项 → 生成修改批次 → 部分接受

### 4.1 项目问题列表

每个问题记录位置、依据、影响、建议和处理状态。支持跳转、稍后处理和不采纳，不自动修复全部发现。

选择一个问题后，在当前任务中生成对应批次。无关发现先记录，不顺手并入当前修改。

### 4.2 跨文件关系与部分接受

说明涉及各文件的必要性，并提示哪些片段应一起接受。例如修改接口时，标明定义、调用方和测试之间的关系。

依赖提示是审查辅助，不能保证任意片段组合都能运行。关联修改未接受时，应明确显示仍需处理的事项。

### 4.3 可编辑候选草稿

支持用户在应用前修改候选内容，再预览实际差异并接受。草稿与业务文件分开；应用前再次验证源文件版本。

接受后在普通编辑器里继续手动修改的方式保留，不强迫用户始终在候选界面操作。

### 4.4 验收标准

- 项目检查可形成有依据、可跳转、可单独处理的问题列表。
- 用户能选择其中一个问题生成跨文件批次，其他问题保留原状态。
- 部分接受后能识别未处理关联项，不将整个问题自动标记为已解决。
- 编辑草稿后，预览与实际应用结果一致；源文件变化时阻止过期应用。

## 5. 第三阶段：验证闭环与安装交付

### 5.1 版本与冲突处理

补强从上下文读取、候选生成到应用之间的版本检查。区分“待修改文件变化”和“参考文件变化”：前者必须阻止过期应用，后者根据可追踪信息提示重新核对。

第一阶段先保证旧批次不覆盖新代码；完整的读取追踪、冲突后重新生成与更细粒度处理放在本阶段。若无法观察所有模型读取行为，应明确覆盖范围，不宣称完全检测上下文过期。

### 5.2 验证操作

应用后提供与修改相关的验证命令，展示命令及工作目录，由用户选择执行，并把实际结果带回讨论。

区分静态检查、实际执行结果和建议验证。失败后给出原因与下一批建议，不默认进入持续自动修复循环。涉及外部系统或业务副作用的命令应单独说明影响。

### 5.3 安装与文件操作

- 形成 VSIX 安装包，减少日常使用对 F5 调试启动的依赖。
- 改善 Node.js 和 Codex 路径发现，避免依赖开发者机器的固定路径。
- 逐步支持新增文件；删除和重命名采用明确的独立操作及相应验证。
- 扩展真实宿主测试，覆盖候选生成到应用、保存、继续讨论的完整流程。

### 5.4 验收标准

- 用户可安装扩展并完成连接、讨论、预览、部分接受和继续编辑。
- 验证结果有实际执行依据，失败不会触发未经选择的后续修改。
- 文件冲突、保存失败和连接中断不会静默丢失用户修改或任务记录。
- 新增文件不覆盖已有内容；尚未支持的文件操作明确拒绝。

## 6. 最后阶段：双模型审查

双模型审查明确安排在整个实施顺序的最后，在持续协作、项目检查、候选编辑、验证闭环和安装交付完成并稳定后再实施，不作为前面阶段的依赖。

届时由第二个模型辅助审查候选修改的正确性、遗漏和跨文件影响，给出依据及分歧供用户判断。审查结果不自动触发修改，也不替代实际测试和用户选择。

## 7. 暂缓事项

暂不优先实现第二套 harness、多代理自治开发、全项目向量索引、自动修复全部问题，以及要求用户维护大量状态文件的固定流程。

当持续讨论、上下文同步、部分接受和验证体验稳定后，再根据实际瓶颈判断是否引入这些能力。

## 8. 实施边界与交付方式

产品开发可以按上述较大的阶段推进；对业务项目的每批修改仍须保持可理解、可审查。

- 阶段内按模块实现和验证，最终交付可连贯使用的工作流程。
- 先实现第一阶段及其关键集成验证，再扩展项目问题列表和候选编辑。
- 双模型审查放在最后，前面各阶段不为它增加额外流程。
- 每次交付同步 README 中的实际行为，不把计划能力写成已实现能力。
- 测试覆盖有状态的关键路径，尤其是用户编辑、部分接受、保存失败和会话重建之间的交互。
- 未完成真实宿主或真实模型验证时，明确记录未验证范围。

首个阶段完成后的目标体验是：用户提出一个开发任务，在多个文件间切换关注点，接受部分建议并自行调整，再继续讨论，而不必反复清空上下文、重新说明需求。
