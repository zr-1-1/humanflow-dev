# 同类工具 UI 与交互调研：HumanFlow 的可借鉴设计

实施跟踪：本轮已在 0.4.0 落地视图、目录搜索、任务草稿、状态同步与按需正文挂载，见 [交付记录](HumanFlow_0.4.0_Delivery.md)。本文的后续调研建议不等于全部进入当前发布范围。

调研日期：2026-09-24。

本次依据官方产品文档与实际打开的开源文件，未安装、操作这些产品，也未做视觉截图对比。产品行为与 HumanFlow 的建议实现分开描述；文档和源码的主分支会变化，不保证所有发行版本一致。

配套方案：[UI、上下文效率与持续协作](HumanFlow_UI_Context_Optimization_Plan.md)。

## 1. 主要结论

最适合 HumanFlow 借鉴的是交互组织方式：按请求导航、讨论与修改关联、编辑器内审查、可见的上下文和执行状态。无需立即复制完整 Agent 产品，也无需为了这些交互重写现有前端技术栈。

优先级建议：

1. 按请求定位、全文搜索、稳定滚动和任务草稿。
2. 每轮附带候选及实际应用记录，提供固定的审查入口。
3. 上下文来源和 Harness 压缩状态可见。
4. 可控的执行中补充输入。
5. 最后考虑分支讨论和检查点恢复，先明确它们是否改变文件。

## 2. 官方产品设计对照

### 2.1 VS Code Copilot：请求导航与编辑器审查

官方文档展示了会话内查找、前后请求跳转、当前请求吸顶，以及从回复中的修改文件进入 Diff 的操作。查找可覆盖未显示在屏幕上的内容；部分折叠内容会在定位时展开。[聊天交互文档](https://code.visualstudio.com/docs/chat/chat-overview)

审查文档将修改汇总、文件差异和检查点联系起来；恢复检查点可同时影响文件及后续对话，但不撤销已完成的终端命令或外部服务操作。[审查与恢复文档](https://code.visualstudio.com/docs/agents/run/review-code-edits)

**对 HumanFlow 的启发：**

- 现有侧边目录继续以用户请求为单位，不按每一条上下文或工具事件增加目录项。
- 补充前后轮快捷导航、当前轮标题和本地查找。搜索应基于记录数据，不能只查当前 DOM 中可见的文本。
- 在每轮末尾附上关联批次摘要，点击后进入“修改”视图或原生 Diff，而非让用户一直滚动到底部。
- HumanFlow 的候选尚未写入文件，因此“接受候选”和其他产品“保留已经发生的编辑”语义不同，不能直接复制按钮名称及执行顺序。

### 2.2 Cursor：执行中输入与支线讨论

Cursor 官方概览区分排队输入和当前回合补充，并介绍了独立的支线讨论、会话搜索及检查点。具体入口和快捷键因界面与上线进度不同，不作为 HumanFlow 的固定规范。[官方概览](https://cursor.com/docs/agent/overview)

文档对检查点的描述是恢复文件，保留聊天消息；这与上述 VS Code 文档描述的恢复语义不同，说明“检查点”不能只以按钮名称定义。

**对 HumanFlow 的启发：**

- 生成期间允许继续写草稿，明确区分“本轮补充”与“下一轮请求”。第一版可以只保存下一条草稿，完成后仍由用户点击发送。
- 实时补充需要实际接入 Harness 的回合引导能力，并显示已提交或未送达状态，不能把文字放进界面就视为模型已收到。
- “解释这个 API”可先作为带引用的追问，后续再考虑独立支线，避免第一版引入复杂分支状态。
- 不采用默认连续执行队列或自动推进目标；HumanFlow 仍保持一批结束后由用户决定下一步。

### 2.3 Continue：上下文可见与局部编辑

Continue 文档描述了侧栏聊天、通过选区和显式引用添加上下文，以及检查实际提示内容的入口。Edit 模式文档说明，当前文件可用于理解上下文，而修改针对指定范围。[聊天机制](https://docs.continue.dev/ide-extensions/chat/how-it-works)、[编辑上下文](https://docs.continue.dev/ide-extensions/edit/context-selection)

**对 HumanFlow 的启发：**

- 在输入区展示附加材料：关注选区、附加文件、引用批次和验证结果，每项可查看来源、移除或更换。
- “读了哪些内容”和“允许修改哪些内容”分开显示。附加文件不应自动扩大写入授权。
- 提供默认精简的上下文明细；原始请求查看仅用于本地诊断，提醒其中可能含项目代码，不默认上传日志。
- 本轮未保存缓冲区与磁盘文件须清晰区分，不能仅靠文件名标签表示已发送哪个版本。

### 2.4 Cline：任务历史、用量与压缩反馈

Cline 官方任务文档把任务作为有独立记录的单位，提供历史查找、恢复及用量信息。其压缩文档描述了接近窗口限制时进行摘要，并展示相关调用；同时说明部分模型可能回退到规则裁剪。[任务管理](https://docs.cline.bot/core-workflows/task-management)、[Auto Compact](https://docs.cline.bot/features/auto-compact)

**对 HumanFlow 的启发：**

- 任务历史使用可搜索列表，至少显示目标、更新时间、当前状态；有可靠数据时再显示用量。
- 将“任务总用量”“当前上下文占用”“本轮输入”区分，不能统一显示一个容易误解的百分比。
- 压缩、裁剪、线程重建分别显示。原始历史可见不代表模型仍持有全文。
- 对摘要保留关键事实的效果做测试，不照搬“所有细节均保留”的宣传表述。

## 3. 已核实的实现方式

### 3.1 Continue 的 Webview 消息协议

实际打开的 [`webviewProtocol.ts`](https://raw.githubusercontent.com/continuedev/continue/main/extensions/vscode/src/webviewProtocol.ts) 中，消息携带 `messageType`、`messageId` 和 `data`。响应复用对应 ID；异步生成器结果分段发送，并区分完成与错误。

实际打开的 [`VsCodeMessenger.ts`](https://raw.githubusercontent.com/continuedev/continue/main/extensions/vscode/src/extension/VsCodeMessenger.ts) 中，打开文件、接受／拒绝差异、应用内容和编辑请求分别交给对应处理器，并与 Diff 管理职责分开。

以上确认的是所读取文件的局部职责，不是对 Continue 全部运行架构、性能或安全性的完整审计。

**建议 HumanFlow 采用相同的职责分离思路，而非复制源码：**

```text
面板操作
  ↓ 带请求 ID、任务 ID 和对象版本的消息
扩展控制器：校验、路由、处理取消
  ├─ 任务与历史服务
  ├─ 候选与应用服务
  ├─ 上下文组装
  └─ Codex 会话适配
  ↓ 状态快照或局部事件
前端状态 → 对应区域更新
```

继续沿用本项目的路径检查、版本校验和用户勾选后应用机制。前端传来的选中项或路径都必须在扩展端重新验证。

### 3.2 Cline 的长列表实现：本次不下源码结论

本次尝试获取 Cline 的聊天组件源码，但读取失败。第三方文章提及其列表渲染技术，本次没有用它们作为已核实的实现依据。

本次核实的是官方交互文档，没有读取 Cursor 内部前端实现。不能据此推断其数据库结构、虚拟列表库或检查点算法。

## 4. HumanFlow 的具体交互草案

### 4.1 页面布局

```text
任务目标 · 当前阶段                         设置
─────────────────────────────────────────────
请求目录          讨论 | 修改(3) | 问题(2)
搜索历史          当前请求标题
                  回答摘要
1. 检查接口       [展开依据] [解释 API]
2. 调整返回值     本轮候选：2 文件 / 4 片段
3. 验证失败       [审查本批]
─────────────────────────────────────────────
附加：关注选区 ×  失败记录 ×  + 添加
需求或追问……
上下文详情                       发送 / 取消
```

这是 HumanFlow 的建议布局，不是竞品截图。窄屏把目录收起，主区采用页签；完整代码差异留在 VS Code 编辑器。

### 4.2 一次请求的展示

请求 → 操作摘要 → 回答 → 关联候选 → 应用结果 → 验证结果，作为同一轮的可定位内容。

各部分按需出现。工具日志默认显示简短状态和数量，展开后查看，避免日志占据主阅读区。

“收到回答”“候选可审查”“已应用”“已保存”“验证通过”分别表达不同事实。候选过期后保留查看和解释入口，但禁用应用。

### 4.3 审查动作

1. 点击本轮的“审查本批”，进入修改列表。
2. 选择文件，原生 Diff 展示当前勾选结果。
3. 对片段提问时引用批次、文件和片段 ID，不复制整段历史。
4. 应用后展示实际结果；未选部分保持明确状态，不能误显示整批已完成。
5. 若源码变化，显示冲突位置和重新生成入口，不让用户从笼统错误里猜原因。

文件切换应保留勾选项；选择变化后旧审查结论失效。跳到下一个待审查文件可作为可选操作，避免强制移动编辑器焦点。

### 4.4 输入草稿与补充请求

第一阶段按任务保存草稿，忙碌时仍可编辑，并清楚显示尚未发送。模型回合失败或取消不清空草稿。

后续支持回合内补充时，使用明确动作“补充本轮”；“作为下一轮发送”保持独立。补充请求附加到哪个回合、是否送达、是否使候选目标改变，都需要有记录。

### 4.5 上下文交互

默认展示“已附加 N 项”；展开后列出文件与版本、引用轮次、摘要或省略范围。实时用量来自后端事件；无法取得时只显示可确定的字符量。

用户引用旧候选时，才把对应必要片段加入模型上下文。查找和展开历史本身是本地操作，不应自动触发模型调用。

## 5. 实现建议与性能边界

### 5.1 先引入稳定身份与状态，不先更换框架

建议逐步为轮次、消息、批次、验证结果分配稳定 ID，增加任务状态版本。示意：

```text
Task
  id / revision / goal / draft
  Turn[]
    id / request / status
    messageIds / batchIds / validationIds

UIState（按任务保存）
  activeView / expandedIds / selectedBatch
  scrollAnchor / draft
```

这是建议数据结构，尚未实现。记录迁移必须保留旧历史；读取旧任务时可分配稳定身份并保存，不每次渲染都重新生成。

### 5.2 减少全量传输和重绘

目前 HumanFlow 多种状态更新都会发布历史等状态。即使前端复用消息节点，全量序列化和跨 Webview 传输也仍有开销。

建议先保留首次加载的完整快照，再为追加消息、进度、批次状态等使用局部更新。每个事件携带任务 ID 和版本；丢失或错序时请求新快照，避免显示部分过期状态。

操作日志可合并同一次命令的开始和完成事件，但原始执行事实不能因此被改写。独立的错误和保存失败应保持可定位。

### 5.3 长列表逐步优化

先做节点复用、收起内容延迟构建和历史分段加载，再根据实测判断是否需要虚拟列表。引入虚拟列表不等于必须引入完整 React 应用。

窗口化渲染需要同时处理：

- 搜索索引位于数据层，覆盖未挂载的记录。
- 跳转时加载目标区段、展开对应内容并恢复键盘焦点。
- 以消息 ID 和相对偏移保存阅读锚点，不只记录绝对 `scrollTop`。
- 用户阅读旧内容时不抢滚动；靠近底部时才跟随新内容。
- 避免卸载用户正在选中的文本或编辑的输入框。

### 5.4 检查点慎重后置

HumanFlow 尚有人工编辑和部分应用流程。若新增检查点，必须先分别定义：恢复讨论、恢复文件、两者同时恢复。

尤其不能把“重新发送旧请求”默认等同于覆盖此后的业务文件。近期优先提供历史查看、引用追问和原生编辑器撤销；真正恢复操作要比较当前文件与检查点基线，并清楚列出受影响文件。

## 6. 对原修改方案的补充排序

| 优先级 | 新增或细化事项 | 验收重点 |
| --- | --- | --- |
| P0 | 轮次稳定 ID、草稿和阅读锚点 | 刷新、折叠和任务切换不丢交互状态 |
| P0 | 每轮关联批次、固定审查入口、原生 Diff | 无需滚动到历史底部才能处理修改 |
| P0 | 历史本地搜索、命中展开、前后轮导航 | 能找到未显示或已折叠的回答与代码 |
| P1 | 上下文标签、来源版本、压缩状态 | 用户能区分本地历史与模型实际上下文 |
| P1 | 局部事件、分段加载 | 长历史下传输和渲染开销可测量地降低 |
| P2 | 回合内补充、支线解释 | 送达对象和状态明确，不混入下一轮 |
| P2 | 检查点与任务分支 | 不意外覆盖人工修改，恢复语义明确 |

先按小规模实现验证交互收益，再考虑框架迁移。界面响应、模型输入量和生成耗时分别测量，不能用“列表变快”推导“上下文变少”。

## 7. 本次调研的使用边界

本次只更新设计文档，不修改产品代码、不新增运行依赖、不安装同类扩展。开源实现仅用于理解架构；若以后直接采用代码或组件，需另行核对对应版本与许可。

资料中的自动执行、自动接受或广泛回滚不直接纳入 HumanFlow。保留项目自身原则：模型提候选，用户审查，插件校验并应用，实际状态决定后续上下文。
