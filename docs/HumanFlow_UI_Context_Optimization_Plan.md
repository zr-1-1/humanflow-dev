# HumanFlow 下一阶段方案：交互、上下文效率与持续协作

更新日期：2026-09-24。

状态：A/B/C 的程序实现与本地验收已交付于 0.4.0，详见 [实施与验证记录](HumanFlow_0.4.0_Delivery.md)。持续线程保持实验、默认关闭；真实远程提供方专项验收尚未完成。下文保留制定方案时的基线与设计依据，当前行为以交付记录为准，不授权自动修改用户业务项目。

配套调研：[同类工具 UI 与交互设计](HumanFlow_UI_Interaction_Research.md)，包含 VS Code Copilot、Cursor、Continue、Cline 的官方资料，以及已核实的 Continue 消息协议源码。

## 1. 结论与目标

下一阶段优先完善日常协作：让用户快速定位讨论、理解修改、审查候选，并减少每轮重复传入的内容。联网作为独立扩展，不作为本阶段依赖。

保留原愿景：人掌握方向，AI 可以广泛读取，但修改和解释的速度应让人跟得上。核心目标是：

- 人的目标、决策和工程约束能够持续生效。
- 每批修改围绕一个逻辑意图，范围可审查。
- 简单问题简短回答，复杂问题按需展开依据与背景。
- 接受、部分接受、手动编辑、撤销和验证后，可以自然继续讨论。
- 复用现有 Codex Harness，不重复建设 Agent 循环和模型压缩引擎。

设计依据：[工程协作愿景](HumanFlow_AI_Engineering_Workflow_Design_update.md)、[后续实施计划](HumanFlow_Next_Steps.md)。本文细化下一阶段工作，当前交付行为仍以对应版本和代码为准。

## 2. 当前基线与已知缺口

### 2.1 交付与草稿边界

- 已生成的 UI 优化安装包为 `dist/humanflow-0.3.3.vsix`，包括按请求分组的目录、折叠、固定输入区和阅读位置保留。
- 工作区存在未发布的联网草稿，`package.json` 已预置为 `0.3.4`，不表示 `0.3.4.vsix` 已生成或验收。
- 联网草稿与本方案分开验收；不能直接打包整个工作区并宣称仅交付 UI 和上下文优化。
- 已有任务恢复、关注点切换、候选预览、部分应用、候选草稿、问题列表和可选验证等基础能力。

### 2.2 当前上下文行为

代码依据：[`task-state.mjs`](../src/vscode/task-state.mjs)、[`extension.cjs`](../src/vscode/extension.cjs)、[`suggestion-session.mjs`](../src/codex/suggestion-session.mjs)。

| 内容 | 当前处理方式 | 主要问题 |
| --- | --- | --- |
| 讨论历史 | 从后向前选取，序列化大小合计最多 60,000 字符；遇到超预算条目即停止 | 较早内容被省略，不是语义摘要；大条目可能挤掉大量讨论 |
| 历史候选 | 原始候选代码进入本地讨论记录，并可能再次发送 | 已处理候选仍消耗后续上下文 |
| 文件内容 | 携带项目内打开的未保存文件，以及跟踪过的修改文件当前内容 | 与本轮无关的整文件可能反复发送 |
| 应用结果 | 最新记录保留准确片段，较早记录简化为文件与数量 | 可能与讨论中的应用说明重复，记录仍会累积 |
| 整个请求 | JSON 超过 300,000 字符时拒绝发送 | 这是本地输入限制，不是 Token 上限，也不包含随后工具返回的内容 |
| 操作面板 | 公开思考摘要和工具进度仅供本轮观察，不写入任务历史 | UI 展示量不能直接用于推算后续输入量 |

界面收起内容不会减少模型输入。减少占用必须调整实际上下文组装方式。

## 3. Harness 自动压缩：已有能力与当前利用方式

### 3.1 Codex 已经具备压缩能力

本机检查到的 CLI 版本为 `codex-cli 0.156.1`。

OpenAI 官方配置参考提供 `model_auto_compact_token_limit`，用于设置自动压缩触发阈值；未配置时使用模型默认值。具体有效阈值需要结合安装版本、模型元数据和配置解析结果确认。[官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

App Server 还提供 `thread/compact/start` 主动压缩接口，压缩进度通过 `contextCompaction` 的开始和完成事件展示。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server#trigger-thread-compaction)

因此不能把现状描述为“底层没有自动压缩”。应区分 Harness 的线程压缩，与插件如何保存、选取和重新注入任务记录。

### 3.2 当前 HumanFlow 不延续同一模型线程

当前面板每轮执行以下流程：

```text
本地任务记录与当前文件
        ↓
buildContext 重新组装请求
        ↓
thread/start 创建临时线程（ephemeral: true）
        ↓
本轮推理、读取文件和生成建议
        ↓
关闭客户端，清除 threadId
        ↓
下次追问从本地记录重新组装
```

由此可确认：

1. 插件没有调用 `thread/compact/start`，也没有专门展示压缩事件和上下文用量。
2. 某轮内部是否实际触发 Harness 自动压缩，不能只根据插件代码判断；尚未做阈值触发与真实提供方验证。
3. 即使当前临时线程发生压缩，插件也没有把其压缩后的线程状态作为下一轮上下文继续使用。
4. 本地 60,000 字符历史筛选和 300,000 字符请求检查发生在发送之前，Harness 无法补回插件已省略的历史，也无法接管本地直接拒绝发送的请求。

DeepSeek 模型目录中的 `auto_compact_token_limit: null` 不能直接解释为“自动压缩关闭”。它只说明该目录没有给出明确数值；当前有效阈值和压缩能否成功仍需实测。目录里的 `truncation_policy` 也不能等同于完整会话的语义压缩策略。

### 3.3 对优化路线的调整

优先让 Harness 管理线程内部的压缩；HumanFlow 管理任务目标、代码事实、接受结果和用户可见记录。先补观测和兼容性验证，再决定是否增加插件级模型摘要。

| 路线 | 优点 | 代价与适用范围 |
| --- | --- | --- |
| 每轮重建并精简输入 | 保持当前行为，容易明确同步当前代码和实际结果 | 重复输入仍存在，无法延续线程压缩状态；适合近期改进和恢复兜底 |
| 同一任务复用线程 | 可利用 Harness 的连续上下文和压缩，减少手动拼接历史 | 必须准确同步手动编辑、撤销、部分应用、切换服务及失败恢复；需要专项验证 |

建议近期先做确定性的去重、记录分层与用量展示，同时验证持续线程。在验证通过前不直接切换默认会话策略。

持续线程的试验规则：

- 同一任务、工作区和提供方内连续讨论，优先复用现有线程。
- 用户接受修改、手动编辑或撤销后，明确发送实际结果及受影响代码；历史候选始终不等于当前代码。
- 切换任务、提供方或遇到不可恢复错误时，重建线程，以本地任务状态和当前代码恢复。
- 跨进程恢复需要持久线程及 `thread/resume` 等配套策略，不能仅保留当前临时线程的 ID。
- 开始和完成压缩时更新状态；没有实际事件时不宣称已压缩。
- 持续线程不意味着每轮只计费新增文本；缓存、服务端输入用量和压缩开销需要分别测量。
- 不在后台无限压缩或反复重试；压缩失败要有明确恢复路径。

## 4. 前端 UI 与交互

### 4.1 从长页面改为讨论与审查工作区

| 区域 | 下一步设计 | 目标 |
| --- | --- | --- |
| 顶部状态栏 | 显示可编辑目标、关注对象、当前阶段；低频设置放入设置入口 | 随时知道正在处理什么 |
| 左侧请求目录 | 请求标题、完成或失败状态、待审查或部分应用标记；支持本地搜索 | 找到某轮讨论及其结果 |
| 主区 | “讨论／修改／问题”切换，展示待处理数量 | 避免候选和问题埋在历史底部 |
| 修改区 | 文件列表、增删统计、片段选择；完整差异在 VS Code Diff 编辑器查看 | 降低长代码在面板内的阅读成本 |
| 输入区 | 保留任务级草稿；支持引用回复、修改片段或问题继续提问 | 减少复制粘贴和重复解释 |

宽屏可并排展示讨论和修改列表；窄屏切换视图，避免同时挤入多栏。切换视图和后台状态刷新都应保留滚动位置、折叠状态、勾选项与输入草稿。

目录中的“完成”表示本轮回答结束；“已应用”“已保存”“验证通过”分别表达不同事实，不混用。

### 4.2 按对象操作

在对应内容旁提供“解释这个 API”“为什么这样改”“仅处理此项”“引用并追问”。操作携带稳定的轮次、批次或问题 ID，并可预览将引用的内容。

Discuss、Inspect、Compare、Review 等继续作为自然语言能力，不要求用户经过固定模式切换。对“仅解释／仅审查”请求，执行层应保持不能应用新增候选的明确边界。

### 4.3 输出分层

默认显示“改什么、为什么、影响什么、验证到哪一步”；长依据和 API 背景按需展开。

区分两种展开：已有正文的本地展开不调用模型；“进一步解释”会发起新请求，应在交互上明确。只把长输出折叠不能减少生成用量，需要配合简短默认回答。

## 5. 上下文组织与预算

### 5.1 三层记录

| 层次 | 内容 | 发送方式 |
| --- | --- | --- |
| 完整本地记录 | 原始对话、候选全文、操作详情 | 可查看和回查，不默认全量发送 |
| 任务状态 | 目标、已确认决策、约束、未解决问题、当前步骤 | 稳定携带必要字段 |
| 本轮材料 | 相关讨论、当前代码、应用结果、验证证据 | 按关联性和预算选择 |

候选全文与审查、应用所需精确快照仍要保留；减少的是模型输入，不是删除用户历史或削弱应用前校验。

### 5.2 先实施确定性的精简

1. 旧候选默认只传批次目的、文件及处理状态；用户明确讨论该候选时，再附必要片段。
2. 关注选区已包含在文件正文中时，以位置引用，避免重复发送。
3. 优先当前关注文件、当前批次关联文件和用户附加文件，避免所有历史跟踪文件永久进入每轮。
4. 应用、保存、撤销和验证结果采用结构化记录，减少聊天正文与结果字段的重复表达。
5. 为各类材料分配预算，保留最新请求、明确约束和关键未解决事项；不能只从尾部截取。
6. 超预算时明确提示省略范围或要求缩小范围，不静默裁掉当前请求、关键约束或待应用修改。

新线程没有旧基线时，哈希和增量不能替代完整上下文。未保存文件被排除正文后仍需标记状态；模型需要该文件时，应取得当前编辑器内容，不能退回磁盘旧内容。

### 5.3 上下文明细与用量

面板增加可折叠的“本轮上下文”：

- 携带的文件、来源是编辑器还是磁盘、内容版本。
- 携带的历史轮次、引用批次及省略范围。
- 分项字符量，以及服务端实际返回的 Token 用量（可获得时）。
- 当前是新建线程、复用、恢复还是发生了压缩。

字符量、Token 用量、缓存命中和实际费用是不同指标。没有可靠数据时显示未知，不用字符数冒充 Token 数或费用。

### 5.4 摘要和固定决策

先提供用户可固定和编辑的目标、约束、决策。固定决策引用原始轮次，并区分“用户确认”“模型建议”“待核实”。

待 Harness 压缩和线程复用测试完成后，再判断重建兜底是否需要插件级语义摘要。若增加摘要：记录覆盖范围和生成版本，保留原文，不在每轮自动追加摘要调用；已撤销决策、未应用候选和已过期验证不得被总结成当前事实。

## 6. 修改范围与审查效率

保留“大范围读取、围绕单个意图修改”。现有 12 文件和 100,000 字符上限是防失控限制，不代表推荐审查规模。

增加任务级修改预算：允许的路径、文件数量、增删行数。第一阶段先确定性检查这些可观测指标；函数边界和接口语义需要语言支持，不能声称已完整覆盖。

超限候选可以查看和讨论，但应用前必须拆分或明确调整允许范围。不要为了满足数字预算拆坏同一个必需的跨文件变更。

关联片段以“建议一起审查的修改组”呈现，依赖关系注明是模型建议；不能将其等同于证明正确的自动依赖分析。采用草稿或更改选择后，使不再适用的审查结论失效。

## 7. 应用与验证闭环

应用后展示实际接受片段、保存成功或失败、剩余未处理项和验证状态。主要操作为“查看实际差异”“运行相关验证”“分析失败”“继续讨论”。

验证记录关联批次及相关代码版本。代码变化后，旧验证结果标记为需要重验；退出码为零不等于所有语义正确。

完整终端输出不默认发送模型。先设计受控的输出采集或用户选取方式，限制长度并处理敏感内容，再提供“分析这次失败”。现有 Tasks 实现只记录退出码，不能假定已经具备完整输出采集能力。

失败不自动进入修复循环。保存失败也不自动回滚或重复应用，以编辑器实际内容为准。

## 8. 分阶段实施与验收

| 阶段 | 实施范围 | 主要验收 |
| --- | --- | --- |
| A：使用效率与观测 | 主区视图切换、目录状态、本地搜索、草稿保留；候选和代码去重；上下文明细；压缩与用量事件展示 | 长讨论可定位；状态刷新不打断阅读；输入量下降且代码事实不丢失 |
| B：连续任务与 Harness 复用 | 固定目标和决策；持续线程试验；真实压缩验证；断线和重启恢复；按对象解释 | 编辑、撤销、部分应用后继续讨论准确；压缩后仍保留关键约束；不依赖失效线程 |
| C：可控修改与验证 | 修改预算、关联审查组、验证绑定版本、受控错误反馈 | 超范围候选不能直接应用；过期验证可识别；保存失败和冲突不覆盖用户内容 |

阶段 A 不必等待联网或第二套 Harness。阶段 B 先以可回退的策略试验，确认真实提供方兼容后再改默认行为。避免同时改变上下文选择、线程生命周期和写入流程，导致故障难以定位。

### 8.1 首批建议涉及模块

- `media/panel.html`、`panel.css`、`panel.js`：视图、目录、输入草稿、上下文展示；减少无关状态更新引发的整块重绘。
- `src/vscode/task-state.mjs`：原始历史、结构化结果与模型输入分离；增加存储迁移。
- 新增小型上下文组装模块：预算、引用、去重及可解释的选择结果。
- `src/codex/turn-progress.mjs` 与会话层：适配安装版本实际提供的用量和压缩事件。
- `src/vscode/extension.cjs`：协调任务、上下文和面板，逐步抽离新增职责，不做无关大重构。

### 8.2 量化评估

使用固定的合成长任务记录，对比优化前后，记录实际结果而不预先承诺节省比例：

- 10／30／100 轮讨论下的请求字符量和各组成占比。
- 存在大候选、多次部分应用、多文件未保存内容时的输入量。
- 有真实服务端数据时，记录输入、缓存、输出和压缩相关用量；单独记录首个可见响应及完成耗时。
- 100 轮历史下目录定位、视图切换和状态更新的响应情况。
- 从找到某轮讨论到打开候选差异所需操作数。

### 8.3 必须覆盖的正确性场景

1. 接受部分修改后再手动编辑，模型获得当前代码而不是旧候选。
2. 未保存文件没有静默替换成磁盘版本。
3. 代码变更后旧候选不可应用，验证结果不会继续显示为当前有效。
4. 长历史省略或压缩后，用户目标、约束、未解决事项仍可追溯。
5. 取消、超时、任务切换和重启不会混入迟到结果或其他项目记录。
6. 新旧任务记录迁移不丢失原始讨论，界面草稿按任务隔离。
7. 同一线程的主动压缩、自动阈值触发及失败恢复分别验证；不能用主动压缩成功代替自动压缩实测。
8. Codex 和 DeepSeek 路径分别核实；模型替身测试不表述为远程提供方成功。

## 9. 暂缓事项与交付边界

暂缓第二套 Harness、多代理自动开发、全项目向量索引、自动修复全部问题及复杂的用户熟悉度画像。先用明确的“简短／展开解释”反馈改善输出。

联网草稿继续独立处理。当前已验证工具调用到本机模型替身的链路和指定网页读取；DuckDuckGo 遇到验证码，Tavily 和真实 DeepSeek 联网回合尚未完整验证。不能将这些草稿能力混写为稳定发布功能。

每批交付同步文档、对应测试和 VSIX 版本，保留旧安装包，明确未验证范围。本文创建不改变现有模型配置、业务项目文件或已生成安装包。
